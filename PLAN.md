# Чорновий план системи

**Тема:** Розроблення інтелектуальної мультисенсорної системи моніторингу параметрів приміщення та стану обладнання.

**Статус:** чернетка, 2026-11-14, оновлено за відповідями на відкриті питання. Лише план, реалізацію ще не розпочато.

Позначки: **(вирішено)** сказав або прямо схвалив автор; **(пропозиція)** запропоновано, автор не заперечував, підтвердити остаточно.

## 1. Головна ідея

Універсальність **(вирішено)**: об'єктом моніторингу може бути будь-яке обладнання чи приміщення. Система не прив'язана до одного типу об'єкта, модулі складаються з універсальної бази й змінної комплектації.

## 2. Апаратна частина

| Що | Рішення |
|---|---|
| Виконання | Готові dev-борди на макетках, без власної друкованої плати **(вирішено)** |
| Повна база | ESP32-S3 **(вирішено)** |
| Компактна база | ESP32-C3 **(вирішено)** |
| Ролі баз | Бази рівноправні, окремих ролей немає; до C3 просто можна підключити менше **(вирішено)** |
| Комплектація | Універсальна база в кількох варіантах + змінні датчики й розширення **(вирішено)** |
| Живлення | Від розетки 5 В або автономне на 1, 2 чи 4 акумулятори 18650 **(вирішено)** |
| Енергоефективний режим | Окреме налаштування модуля **(вирішено)** |
| Вимірювання напруги живлення | Дільник напруги відкладено **(вирішено)** |
| Корпуси | Друк на Bambu Lab A1 mini, поле 180×180×180 мм; принтер не є об'єктом моніторингу **(вирішено)** |

Наявні плати (зчитано esptool):

- 3 × ESP32-S3, rev v0.2, flash 16 МБ, PSRAM 8 МБ, нативний USB. Модель імовірно клон DevKitC-1 / YD-ESP32-S3 (припущення).
- 2 × ESP32-C3, rev v0.4 (C3FH4), flash 4 МБ, без PSRAM, нативний USB. Імовірно C3 SuperMini (припущення).

## 3. Програмна частина

| Складова | Рішення |
|---|---|
| Прошивка | ESP-IDF **(вирішено)**; одна кодова база під обидва чипи **(пропозиція)** |
| Wi-Fi | Мережу (основну і запасну) вводять на сайті під час додавання модуля, сайт запам'ятовує введене; одна назва мережі на всі точки доступу **(вирішено, 2026-11-14 замість вшивання в прошивку)** |
| Додавання модуля | Кнопка «Додати модуль» на сайті: вибір COM-порту (Chrome/Edge, Web Serial), сайт сам визначає чип, прошиває повний образ із сервера з показом відсотків і записує в модуль Wi-Fi та адресу сервера; модуль сам з'являється в таблиці **(вирішено)** |
| OTA | Оновлення прошивки по Wi-Fi з інтерфейсу вже на етапі 1; два слоти прошивки (і на C3 з 4 МБ), без автоматичного відкату **(вирішено)** |
| Зв'язок | Wi-Fi + MQTT, брокер у Docker **(пропозиція)**; основний сценарій: модулі з'єднуються із сервером на VPS через інтернет, локальна мережа другорядна **(вирішено)** |
| Безпека MQTT | Окремий логін і пароль на кожен модуль; TLS вмикається в налаштуваннях, на VPS обов'язковий **(вирішено)** |
| Сервер | Docker, Python FastAPI **(вирішено)**; розробка на домашньому ПК, повна система розгортається на VPS **(вирішено)** |
| База даних | PostgreSQL **(вирішено)** + TimescaleDB **(вирішено)** |
| Інтерфейс | React, живі графіки, моніторинг і керування, українською **(вирішено)** |
| Вигляд інтерфейсу | Темна тема; поки лише основні примітиви; «стиль Excel» означає табличне відображення і мінімум карток, без редагування в комірках; тривоги підсвічуються кольором комірки (червоний, жовтий); вивантаження в Excel/CSV не потрібне **(вирішено)** |
| Вхід | Один обліковий запис без ролей, логін і пароль із файла `.env` **(вирішено)** |
| Веб-сторінка на модулі | Не потрібна **(вирішено)** |
| Репозиторій | Один, з папками для прошивки, сервера, інтерфейсу і 3D-моделей корпусів **(вирішено)** |

Потік даних: модуль → MQTT-брокер → сервер (FastAPI) → TimescaleDB → інтерфейс (живі дані через WebSocket). Команди йдуть у зворотному напрямку через MQTT.

## 4. Масштаб: 200 модулів

Вимога **(вирішено)**: закласти підтримку 200 модулів.

Навантаження: 200 модулів × ~10 показників × раз на секунду ≈ 2000 записів/с ≈ **170 млн записів на добу**.

| Рівень | Як витримати масштаб |
|---|---|
| Wi-Fi | Кілька точок доступу з однією назвою мережі **(вирішено)**; перепідключення з випадковою затримкою, щоб модулі не ломилися одночасно **(пропозиція)** |
| Модуль | Ідентифікатор за MAC, самореєстрація на сервері, сигнал втрати зв'язку (MQTT Last Will) **(пропозиція)** |
| База | Запис пачками, стиснення і зведення (агрегація) старих даних **(пропозиція)** |
| Інтерфейс | Таблиця модулів із пошуком, групи, зведення по групах **(пропозиція)** |
| Керування | Масові дії по групах; OTA хвилями, а не всім одразу **(пропозиція)** |

Налаштування:

- Інтервал надсилання: за замовчуванням 1 с, налаштовується для окремого модуля і для групи **(вирішено)**.
- Гібридний режим надсилання (опційно, вмикається для модуля): поки показники в налаштованому діапазоні норми, модуль надсилає рідко (наприклад раз на хвилину), а щойно щось поза нормою, надсилає негайно **(вирішено)**. Етап 2, деталі в розділі 5.
- Термін зберігання історії задає користувач системи в інтерфейсі **(вирішено)**. За замовчуванням: сирі дані 7 днів, середні за хвилину 90 днів, середні за годину без обмеження **(вирішено)**.
- Програмний симулятор плат не робимо **(вирішено)**.

## 5. Етапи

1. **Основа (голі плати, без датчиків)** **(вирішено)**. Модуль передає те, що має сама плата: стан зв'язку, рівень Wi-Fi (RSSI), час роботи, температура чипа **(пропозиція)**; напругу живлення відкладено до появи дільника. Керування: світлодіод, перезапуск, OTA. Сервер, база, інтерфейс з входом, таблицею модулів і живими графіками.
2. **Датчики і змінна комплектація** **(вирішено)**. Набір датчиків не фіксуємо й не обмежуємо. Модуль сам повідомляє серверу, що до нього підключено **(пропозиція)**. Формат опису датчиків (тип, одиниці, діапазон) визначаємо на цьому етапі. Дані з датчика за замовчуванням надсилаються сирими; фільтрація прямо на мікроконтролері до надсилання, яку можна вмикати, вимикати й налаштовувати **(вирішено)**.
   - Гібридний режим надсилання **(вирішено)**: модуль вимірює щосекунди, але в нормі надсилає рідко. Межі норми задаються в інтерфейсі й зберігаються на модулі. При виході за межі модуль надсилає негайно і переходить на частий інтервал, доки показник не повернеться в норму. Разом із тривогою надсилає останні 30–60 с вимірів (передісторію події).
   - Втрата інтернету: пропуск даних допустимий, бо пам'ять модуля обмежена **(вирішено)**. Буфер лише в оперативній пам'яті по колу: коли місце скінчилося, найстаріші дані затираються; у flash не пишемо, щоб не зношувати. Без зв'язку модуль зберігає середні за хвилину, а тривоги й виходи за межі зберігає завжди і надсилає першими після відновлення. Розмір буфера є налаштуванням модуля (орієнтовно S3 близько доби хвилинних даних, C3 кілька годин; не виміряно). В інтерфейсі пропуск видно на графіку як розрив **(вирішено)**.
   - Екрани **(вирішено)**: екран є типом доповнення до модуля, на одній платі їх може бути кілька (гнучка модульна архітектура). Перший наявний: OLED 0,96", 128×64, I2C, SSD1306/SSD1315. У кожного екрана свої налаштування на сайті: увімкнено, яскравість, гасіння через N секунд. Що показувати, обирається з сайту списком з одного чи кількох показників модуля; службові дані (назва, зв'язок, версія) є звичайними пунктами цього списку. Види відображення: один показник великим, списком разом, по черзі зі зміною кожні N секунд. Нічого примусового поверх немає (ні рядка стану, ні тривоги). Показ даних із сервера на екрані відкладено.
3. **Автоматизація** **(вирішено)**. Правила автоматизації, планування завдань. Сповіщення поки лише в інтерфейсі, з можливістю додавати власні канали (наприклад Telegram).
4. **«Інтелектуальна» частина** **(вирішено)**: самонавчання норми, виявлення аномалій. Відкладено, поки не робимо.

## 6. Відкриті питання

1. Конструктор прошивки (ідея на потім, без рішення): збирати прошивку лише з потрібних доповнень і можливостей (наприклад фільтрації), щоб не вантажити в плату все. Попередні шляхи: одна універсальна прошивка, де доповнення вмикаються налаштуваннями (як зараз), або збирання на сервері під вибраний набір. Поки доробляємо як є, обміркуємо пізніше.

Відкладено до свого часу: дільник для вимірювання напруги живлення; формат опису датчиків (етап 2); дані з сервера на екрані модуля; виявлення присутності людей за Wi-Fi (CSI): аналіз зроблено, на думку автора на практиці працює погано, рішення не ухвалено.

Примітка: захист диплома буде з іншого місця, де треба підключити й показати модуль, тому для демонстрації потрібен сервер на VPS.
