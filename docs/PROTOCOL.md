# Протокол обміну модуль ↔ сервер (версія v1, етап 1)

Статус: робочий договір між прошивкою і сервером, 2026-11-14 (розділ 6 додано того ж дня; 2026-11-15 додано обробку на модулі: фільтри, межі норми, гібридний режим, прошивка 0.3.0; того ж дня додано доповнення й екрани, розділ 3.7, прошивка 0.4.0). Якщо щось змінюється, змінюємо цей файл і повідомляємо обидві сторони.

## 1. Загальне

| Що | Значення |
|---|---|
| Ідентифікатор модуля `<id>` | MAC Wi-Fi STA (`esp_read_mac(..., ESP_MAC_WIFI_STA)`), 12 шістнадцяткових символів у нижньому регістрі без двокрапок, напр. `a0b1c2d3e4f5` |
| Префікс тем | `dm/v1/<id>/...` |
| Кодування | JSON у UTF-8, без BOM; числа як числа, логічні як `true`/`false` |
| MQTT | 3.1.1 або 5; `client_id` = `<id>`; clean session = true; keepalive 30 с |
| Логін MQTT | `username` = `<id>`, `password` = видає сервер при реєстрації (розділ 2) |
| Порти брокера | 1883 без TLS; 8883 з TLS (вмикається на сервері, на VPS обов'язково) |
| Час | `ts` у мілісекундах Unix (UTC). Якщо SNTP ще не синхронізувався, модуль шле `ts: 0`, і сервер ставить час отримання |

Налаштування модуля (до двох мереж Wi-Fi, адреса сервера `SERVER_URL`, хост і порт MQTT, прапорець TLS, токен реєстрації `PROVISION_TOKEN`) записує сайт через USB-порт під час додавання модуля (розділ 6) і модуль зберігає їх у NVS. Значення, вшиті під час збирання (`secrets.h`), лише запасні для розробки: налаштування з NVS мають пріоритет. Для TLS модуль перевіряє сертифікат сервера через вбудований набір кореневих сертифікатів ESP-IDF (`esp_crt_bundle`).

## 2. Реєстрація (отримання пароля MQTT)

Модуль, у якого в NVS ще немає пароля MQTT, робить HTTP(S)-запит:

```
POST <SERVER_URL>/api/provision
Content-Type: application/json

{"id": "a0b1c2d3e4f5", "chip": "esp32s3", "fw": "0.1.0", "token": "<PROVISION_TOKEN>"}
```

Відповіді:

| Код | Тіло | Що робить модуль |
|---|---|---|
| 200 | `{"username": "a0b1c2d3e4f5", "password": "<32 символи>"}` | Зберігає пароль у NVS (простір `dm`, ключ `mqtt_pass`) і підключається до MQTT |
| 401 | `{"detail": "..."}` | Невірний токен: повторити через 5 хв |
| 409 | `{"detail": "..."}` | Модуль уже зареєстрований, а пароля в нього немає (наприклад, після стирання flash). Користувач має натиснути в інтерфейсі «Скинути пароль MQTT»; модуль повторює запит раз на 1 хв |

Якщо брокер відхиляє логін (CONNACK «not authorized» / «bad username or password») 3 рази поспіль, модуль стирає пароль із NVS і знову проходить реєстрацію.

## 3. Теми

| Тема | Напрям | QoS | Retained | Призначення |
|---|---|---|---|---|
| `dm/v1/<id>/status` | модуль → сервер | 1 | так | Стан модуля; `offline` ставить Last Will |
| `dm/v1/<id>/telemetry` | модуль → сервер | 0 | ні | Показники |
| `dm/v1/<id>/cmd` | сервер → модуль | 1 | ні | Команди |
| `dm/v1/<id>/cmd/ack` | модуль → сервер | 1 | ні | Відповіді на команди |
| `dm/v1/<id>/config` | сервер → модуль | 1 | так | Налаштування модуля |

Права модуля на брокері: публікувати лише в `status`, `telemetry`, `cmd/ack` своєї теми; підписуватися лише на `cmd` і `config` своєї теми.

Модуль після підключення: підписується на `cmd` і `config`, потім публікує `status` з `state: "online"`.

### 3.1. `status`

```json
{
  "state": "online",
  "chip": "esp32s3",
  "fw": "0.1.0",
  "idf": "v5.3.1",
  "ip": "192.168.1.23",
  "ssid": "MyWiFi",
  "reset_reason": "poweron",
  "config_rev": 3,
  "led": "off",
  "caps": ["led", "restart", "ota", "filters", "limits", "hybrid", "addons", "display"],
  "addons": [
    {"id": "led", "type": "led", "builtin": true, "ok": true, "hw": "RGB WS2812, GPIO48", "state": "off"},
    {"id": "oled1", "type": "display", "ok": false, "error": "екран не відповідає за адресою 0x3C (SDA GPIO8, SCL GPIO9)"}
  ]
}
```

| Поле | Тип | Обов'язкове | Опис |
|---|---|---|---|
| `state` | `"online"` \| `"offline"` | так | |
| `chip` | рядок | так при online | `esp32s3` або `esp32c3` |
| `fw` | рядок | так при online | Версія прошивки з `esp_app_desc_t.version` |
| `idf` | рядок | ні | Версія ESP-IDF |
| `ip`, `ssid` | рядок | ні | |
| `reset_reason` | рядок | ні | `poweron`, `sw`, `panic`, `wdt`, `brownout`, `deepsleep`, `ota`, `other` |
| `config_rev` | ціле | ні | Номер застосованої конфігурації (розділ 3.5); 0, якщо ще не отримано |
| `led` | `"on"` \| `"off"` \| `"blink"` | ні | Поточний стан світлодіода |
| `caps` | масив рядків | ні | Які команди й можливості модуль підтримує. `filters`, `limits`, `hybrid` означають підтримку відповідних полів `config` (розділ 3.5, з прошивки 0.3.0). `addons` і назви типів доповнень (`display`) — розділ 3.7, з прошивки 0.4.0 |
| `addons` | масив | ні | Стан доповнень (розділ 3.7): вбудовані (`builtin: true`, напр. світлодіод) і налаштовані з сайту. `ok` — працює; `error` — чому ні |

Last Will (задається при підключенні): тема `dm/v1/<id>/status`, QoS 1, retained, тіло `{"state":"offline"}`. Перед плановим перезапуском модуль сам публікує `{"state":"offline","reason":"restart"}` (або `"ota"`).

Повторно `status` публікується при кожній зміні поля (наприклад, після команди `led` або застосування конфігурації).

### 3.2. `telemetry`

```json
{"ts": 1731621107123, "seq": 42, "values": {"rssi": -61, "uptime_s": 3600, "chip_temp_c": 41.5, "heap_free": 182340}}
```

| Поле | Опис |
|---|---|
| `ts` | Час виміру, мс Unix; 0 якщо час невідомий |
| `seq` | Лічильник повідомлень від старту (для виявлення пропусків), ціле ≥ 0 |
| `values` | Об'єкт «назва показника: число». Назви: латиниця в нижньому регістрі, цифри, `_`, до 32 символів. Нечислові значення сервер ігнорує |

Показники етапу 1:

| Назва | Одиниці | Звідки |
|---|---|---|
| `rssi` | дБм | `esp_wifi_sta_get_ap_info` |
| `uptime_s` | с | `esp_timer_get_time() / 1e6` |
| `chip_temp_c` | °C | вбудований датчик температури (`temperature_sensor`) |
| `heap_free` | байт | `esp_get_free_heap_size()` |

Модуль може надсилати й інші показники: сервер приймає будь-які назви, нічого не треба реєструвати заздалегідь.

Пакетне надсилання: `{"seq": 43, "samples": [{"ts": ..., "values": {...}}, ...], "alarms": [...]}`, виміри від старіших до новіших, останній — поточний. Так модуль надсилає передісторію тривоги (розділ 3.6).

Поле `alarms` (з прошивки 0.3.0, є в кожному повідомленні): масив назв показників, які зараз поза межами норми (розділ 3.5, `limits`); порожній масив — усе в нормі. Сервер порівнює його з попереднім і записує події «Тривога» (рівень `alarm`) і «Повернулося в норму». Якщо поля немає (стара прошивка), стан тривог не змінюється.

Значення в `values` уже пройшли фільтр, якщо його задано (розділ 3.5, `filters`).

Частота: модуль вимірює раз на секунду, а надсилає раз на `interval_s` з конфігурації (за замовчуванням 1 с) або за правилами гібридного режиму (розділ 3.6).

### 3.3. `cmd`

```json
{"id": "7f3c2a10", "name": "led", "params": {"mode": "blink"}}
```

| Команда | `params` | Що робить |
|---|---|---|
| `led` | `{"mode": "on" \| "off" \| "blink"}` | Вбудований світлодіод (на S3 RGB WS2812, на C3 звичайний) |
| `restart` | `{}` | Відповідає `ok`, публікує `offline` з `reason: "restart"`, перезапускається через ~0,5 с |
| `ota` | `{"url": "...", "version": "0.2.0", "size": 912384, "sha256": "<64 hex>"}` | Оновлення прошивки (розділ 4) |

`id` — рядок до 36 символів, унікальний. Невідому команду модуль відхиляє з `status: "error"`.

### 3.4. `cmd/ack`

```json
{"id": "7f3c2a10", "status": "ok", "message": ""}
```

| Поле | Опис |
|---|---|
| `id` | `id` команди |
| `status` | `"ok"` (виконано), `"error"` (не виконано), `"in_progress"` (лише для `ota`) |
| `progress` | 0–100, для `in_progress` |
| `message` | Текст помилки або пояснення, необов'язкове |

Сервер вважає команду без відповіді за 30 с (для `ota` 10 хв після останнього `in_progress`) простроченою.

### 3.5. `config`

```json
{
  "rev": 5,
  "interval_s": 1,
  "hybrid": {"normal_interval_s": 60, "history_s": 60},
  "filters": {"chip_temp_c": {"type": "ema", "alpha": 0.2}, "rssi": {"type": "median", "window": 5}},
  "limits": {"chip_temp_c": {"max": 60, "hyst": 1}, "rssi": {"min": -85, "hyst": 2}}
}
```

| Поле | Тип | За замовчуванням | Опис |
|---|---|---|---|
| `rev` | ціле | — | Номер ревізії, зростає при кожній зміні |
| `interval_s` | ціле 1–3600 | 1 | Як часто надсилати `telemetry` (у гібридному режимі: як часто під час тривоги) |
| `hybrid` | об'єкт або відсутнє | відсутнє = вимкнено | Гібридний режим, розділ 3.6 |
| `hybrid.normal_interval_s` | ціле 1–3600 | 60 | Як часто надсилати, поки всі показники в нормі |
| `hybrid.history_s` | ціле 0–60 | 60 | Скільки секунд передісторії надсилати разом із тривогою |
| `filters` | об'єкт «показник: фільтр» | `{}` = сирі дані | Фільтр на модулі до надсилання |
| `limits` | об'єкт «показник: межі» | `{}` = без контролю | Межі норми |

Фільтр (`filters.<показник>`), застосовується до кожного виміру (раз на секунду):

| `type` | Параметр | Що робить |
|---|---|---|
| `avg` | `window` 2–30 | Ковзне середнє останніх `window` вимірів |
| `median` | `window` 2–30 | Медіана останніх `window` вимірів (прибирає поодинокі викиди) |
| `ema` | `alpha` 0,01–1 | Експоненційне згладжування: `y = y + alpha·(x − y)`; менше `alpha` = плавніше |

Межі (`limits.<показник>`): `min` і/або `max` (хоча б одне, `min < max`), `hyst` ≥ 0 (за замовчуванням 0). Показник переходить у тривогу, коли значення (після фільтра) стає більшим за `max` або меншим за `min`, і повертається в норму, лише коли воно в межах із запасом `hyst` (`≤ max − hyst` і `≥ min + hyst`), щоб стан не перемикався на самій межі.

Модуль застосовує конфігурацію, зберігає її в NVS як рядок JSON (щоб працювати до підключення) і публікує `status` з новим `config_rev`. Показники, яких модуль не має, і невідомі поля ігнорує. Стан фільтра скидається лише для показника, у якого змінився фільтр. Сервер шле лише ті поля, що задані (порожні `hybrid`, `filters`, `limits` не надсилає).

### 3.6. Гібридний режим і передісторія

Модуль вимірює раз на секунду і зберігає в оперативній пам'яті останні 60 вимірів (після фільтра).

- Поки всі показники з межами в нормі, `telemetry` іде раз на `hybrid.normal_interval_s`.
- Щойно якийсь показник вийшов за межі, модуль одразу надсилає пакет `samples` з ще не надісланими вимірами за останні `hybrid.history_s` секунд (передісторія) і поточним виміром, далі надсилає раз на `interval_s`, доки є хоча б одна тривога.
- Коли всі показники повернулися в норму, модуль одразу надсилає поточний вимір із порожнім `alarms` і знову переходить на `normal_interval_s`.
- Без гібридного режиму межі теж працюють: модуль надсилає раз на `interval_s`, а при зміні стану тривоги одразу, але без передісторії.
- Пакет із передісторією обмежено ~12 КБ (буфер MQTT модуля); якщо не вміщається, модуль скорочує передісторію. Виміри без часу (`ts` 0, SNTP ще не синхронізовано) у передісторію не потрапляють.
- Якщо зв'язку немає, повідомлення не надсилаються; зміна стану тривоги буде надіслана першою після підключення (накопичення хвилинних середніх без зв'язку буде окремим кроком).

Сервер чекає даних від модуля в гібридному режимі не `3 × interval_s`, а з урахуванням `normal_interval_s`, перш ніж показати «немає даних».

### 3.7. Доповнення (екрани та інше)

Доповнення — пристрій на платі або підключений до неї: вбудований світлодіод, екран, згодом інші розширення. Усі вони описуються однаково: `id` (унікальний на модулі, `[a-z0-9_-]`, до 16 символів), `type` і налаштування свого типу. Модуль повідомляє стан кожного доповнення в `status.addons` (розділ 3.1); тип, якого прошивка не знає, там буде з `ok: false` і поясненням. На одній платі до 4 доповнень із сайту.

Вбудовані доповнення (`builtin: true`) модуль повідомляє сам, додавати їх не треба. Зараз це світлодіод `led`, ним керує команда `led` (розділ 3.3); у `status.addons` він має ще `driver`, `gpio`, `active_low` (поточне підключення) і `state` (`on`/`off`/`blink`).

Підключення світлодіода можна змінити з сайту, якщо плата не така, як вважає прошивка: запис `{"type": "led", "id": "led", "driver": "ws2812" | "gpio", "gpio": 8, "active_low": true}` у масиві `addons`. `ws2812` — адресний RGB, `gpio` — звичайний світлодіод (`active_low` — світиться при низькому рівні). Без такого запису діє підключення за замовчуванням: S3 — RGB на GPIO48, C3 — звичайний на GPIO8, інверсний. Вивід світлодіода недоступний для інших доповнень.

Налаштовані доповнення приходять у `config` (розділ 3.5) масивом `addons`; модуль перестворює їх лише тоді, коли цей масив змінився. Якщо серед пунктів екрана є назва модуля, сервер додає в `config` поле `name` і надсилає конфігурацію знову при перейменуванні.

```json
"addons": [{
  "type": "display", "id": "oled1", "enabled": true,
  "driver": "ssd1306", "sda": 8, "scl": 9, "addr": 60, "height": 64, "flip": false, "button": 0,
  "brightness": 80, "off_after_s": 0, "view": "list", "cycle_s": 5,
  "items": [{"src": "@name", "label": "Модуль"}, {"src": "chip_temp_c", "label": "Темп. чипа", "unit": "°C"}]
}],
"name": "Цех 1"
```

Тип `display`: монохромний OLED 128×64 або 128×32 на I2C.

| Поле | За замовчуванням | Опис |
|---|---|---|
| `enabled` | `true` | `false` — екран погашено |
| `driver` | `ssd1306` | `ssd1306`, `ssd1315` (команди ті самі) або `sh1106` (часто в екранах 1,3″) |
| `sda`, `scl` | S3: 8, 9; C3: 5, 6 | Виводи GPIO. Кілька екранів на тих самих виводах ділять одну шину I2C (потрібні різні адреси); на S3 можна дві окремі шини, на C3 одну |
| `addr` | 60 (0x3C) | Адреса I2C, зазвичай 0x3C або 0x3D |
| `height` | 64 | 64 або 32 рядки |
| `flip` | `false` | Повернути зображення на 180° |
| `button` | S3: 0, C3: 9 (кнопка BOOT) | Кнопка: будить погашений екран, на ввімкненому гортає сторінки. −1 — немає |
| `brightness` | 100 | Яскравість (контраст) 1–100 % |
| `off_after_s` | 0 | Гасити через N секунд після ввімкнення чи натискання кнопки; 0 — світиться завжди |
| `view` | `list` | `big` — перший пункт великим шрифтом; `list` — пункти рядками (6 рядків на 128×64; якщо більше, сторінки змінюються кожні `cycle_s`); `cycle` — кожен пункт великим по черзі |
| `cycle_s` | 5 | Інтервал зміни пункту чи сторінки, 1–3600 с |
| `items` | `[]` | До 12 пунктів: `src` — назва показника з `telemetry.values` або службовий пункт; `label` — підпис; `unit` — одиниці |

Службові пункти: `@name` (назва модуля із сайту, інакше ідентифікатор), `@id`, `@fw` (версія прошивки), `@ip`, `@ssid`, `@link` (`на зв'язку`, `немає Wi-Fi` або `немає сервера`). Показник, якого модуль не має, показується як `—`; `uptime_s` показується як тривалість. Екран показує лише вибране: примусового рядка стану чи тривоги поверх немає. Шрифти містять латиницю, кирилицю (зокрема і, ї, є, ґ) і `°`.

Модуль недоступні виводи (USB, flash, PSRAM, світлодіод) не використовує і повідомляє помилку в `status.addons`. Якщо екран не відповідає, модуль пробує знову кожні 5 с, тож екран можна під'єднати й пізніше.

## 4. Оновлення прошивки (OTA)

1. Користувач завантажує `.bin` (файл застосунку, не merged-образ) в інтерфейсі. Сервер читає з образу тип чипа і версію (`esp_app_desc_t`) і рахує SHA-256.
2. Сервер надсилає команду `ota` з адресою вигляду `<PUBLIC_URL>/api/firmware/<fw_id>/download?token=<випадковий токен>`. Завантаження без логіна, захист токеном.
3. Модуль перевіряє, що `version` відрізняється від поточної, завантажує файл (`esp_https_ota`), шле `in_progress` приблизно кожні 10 %, перевіряє SHA-256 і розмір.
4. Успіх: `ok`, `offline` з `reason: "ota"`, перезапуск у новий слот. Після старту модуль шле `status` з новою версією `fw`, і сервер позначає оновлення завершеним.
5. Помилка: `error` з `message`, модуль лишається на старій прошивці. Автоматичного відкату після перезапуску немає (за планом).

## 5. Що сервер робить сам

- Перший `status` від нового `<id>` (після реєстрації) створює модуль у таблиці.
- `offline` у статусі або відсутність телеметрії довше за `3 × interval_s + 10 с` (у гібридному режимі за довшим із `interval_s` і `normal_interval_s`) показує модуль як «немає зв'язку».
- `config` публікується retained при зміні налаштувань модуля або його групи і повторно при реєстрації модуля.

## 6. Додавання модуля з сайту (прошивання і налаштування через USB)

Сайт (Chrome або Edge на комп'ютері, сторінка «Додати модуль») працює з платою через Web Serial по нативному USB (USB Serial/JTAG у S3 і C3).

### 6.1. Прошивання

1. Користувач вибирає COM-порт, сайт підключається завантажувачем ROM (esptool-js) і визначає чип.
2. Сайт бере з сервера останній **повний образ** для цього чипа і записує його з адреси `0x0`, показуючи хід у відсотках. Опційно перед записом стирає всю flash.
3. Апаратний перезапуск у прошивку.

Повний образ — один файл із завантажувачем, таблицею розділів і застосунком, записується з адреси 0:

```
idf.py -B build-s3 -D SDKCONFIG=build-s3/sdkconfig merge-bin -o dm_full_s3.bin
```

(або `esptool.py --chip esp32s3 merge_bin -o dm_full_s3.bin @flash_args` у папці збирання). Файл завантажується на сторінці «Прошивки» так само, як файл для OTA: сервер сам розпізнає, що це повний образ (на `0x8000` таблиця розділів), і читає чип і версію з застосунку всередині.

### 6.2. Налаштування через порт

Після старту прошивки сайт відкриває порт (115200 8N1; для USB Serial/JTAG швидкість не важлива) і обмінюється рядками:

- запит від сайту: один рядок JSON, що закінчується `\n`, до 1024 байт;
- відповідь модуля: рядок `DM:` + JSON + `\n`. Усе інше в порту (журнал ESP-IDF) сайт ігнорує, тому журнал можна не вимикати.

Модуль має приймати команди з порту весь час роботи (не лише одразу після старту): сайт може підключитися із затримкою.

**`info`** — сайт надсилає кілька разів (раз на 1 с, до 20 с), доки не отримає відповідь:

```
{"cmd":"info"}
DM:{"ok":true,"id":"a0b1c2d3e4f5","chip":"esp32s3","fw":"0.2.0","configured":false}
```

`configured` — чи є в NVS налаштування з розділу 6.2.

**`provision`**:

```
{"cmd":"provision","wifi":[{"ssid":"MyWiFi","pass":"secret"},{"ssid":"Backup","pass":""}],"server_url":"https://31-77-168-104.sslip.io","mqtt_host":"31-77-168-104.sslip.io","mqtt_port":8883,"mqtt_tls":true,"token":"..."}
DM:{"ok":true,"id":"a0b1c2d3e4f5"}
```

| Поле | Опис |
|---|---|
| `wifi` | 1–2 мережі в порядку пріоритету; `pass` порожній для відкритої мережі. Довжина як у ESP-IDF: `ssid` до 32 байт, `pass` до 64 |
| `server_url` | Без `/` у кінці |
| `mqtt_host`, `mqtt_port`, `mqtt_tls` | Брокер для модулів |
| `token` | `PROVISION_TOKEN` сервера |

Модуль перевіряє поля, зберігає їх у NVS, **стирає збережений пароль MQTT** (щоб пройти реєстрацію на сервері заново), відповідає `ok` і перезапускається приблизно через 1 с. Помилка: `DM:{"ok":false,"error":"текст"}`, нічого не змінюється. Невідома команда: `DM:{"ok":false,"error":"unknown cmd"}`.

### 6.3. Що робить сервер

- Сайт отримує значення для `provision` з `GET /api/provisioning` (потрібен вхід): `server_url`, `mqtt_host`, `mqtt_port`, `mqtt_tls`, `token` з `.env` сервера.
- Якщо модуль із таким `id` уже є і зареєстрований, сайт перед `provision` скидає його пароль MQTT (`POST /api/modules/<id>/reset-credentials`), щоб реєстрація пройшла без 409.
- Після реєстрації модуль з'являється в таблиці; сайт чекає його появи на зв'язку і, якщо користувач задав назву чи групу, зберігає їх.
